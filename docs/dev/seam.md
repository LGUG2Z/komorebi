## 1. Purpose and how to read it

A shared `Backend` seam has to sit between code that is to be shared (windows, containers, workspaces, monitors, commands, event handling) and three platform layers that today do the same jobs in three different ways. A trait written from memory of one platform would bake that platform's assumptions into the other two. This document records what each platform actually does, so that the trait can be derived from facts.

- **Facts** are the tables and the numbered findings, each with a `file:line` citation read on the tips below. Nothing in a table is a proposal.
- **Proposals** are confined to section 7 (consequences). Each consequence is a statement about what the seam must satisfy, with the facts that support it, and is marked CONFIRMED, CORRECTED or TARGET (not true of any current code, but something the seam would have to make true).
- "Not verified" means I read the code and could not settle the point by reading (usually: Apple or Microsoft runtime behaviour, or behaviour that needs a Mac). It does not mean "false".

## Corrections to earlier claims

Things in the plan (`generic-percolating-matsumoto.md`, Step 7 and "Risks") or the progress log that this reading contradicts or refines.

1. **KDE `Backend` method count.** The trait declares **31** methods: 19 required (`K/backend/mod.rs:242-258`, `325-389`, `408-432`) and 12 provided (`:280`, `:311`, `:473`, `:504`, `:529`, `:553`, `:586`, `:597`, `:607`, `:612`, `:617`, `:622`). The plan's "28 (not 31)" matches only if the three derived helpers `is_window`, `window_rect`, `monitor_from_point` (`:612-628`, written in terms of `window` and `monitors`) are left out. Use "28 primitives plus 3 derived".
2. **macOS `monitors()` is not a cache** (already corrected by the kfm A0 report, confirmed). `MacosApi::latest_monitor_information` queries `NSScreen` live and does `MainThreadMarker::new().unwrap()` (`M/macos_api.rs:212-213`), so it panics off the main thread; every caller is already on main (section 3.3). "monitors() reads a cache refreshed by the display callback" is a TARGET (consequence 4).
3. **Consequence 2 is too strong as written.** "`set_rect` is never read back to confirm" is false of macOS: after a direct write the layout reads the frame back to learn whether the app refused the width (`M/window.rs:944-972`, `M/arrival.rs:1-12`), and the animator verifies each journey (`M/animation/animator.rs:902`). KDE returns an optimistic value: `set_rect` writes the requested rect into its own table at once (`K/kwin/state.rs:596-600`, called from `K/kwin/mod.rs:855`). The defensible contract is in section 7.
4. **The KDE `u32` id is not "the compositor's".** The doc comments say so (`K/backend/mod.rs:65`, `K/window.rs:78-81`), but the id is a counter that the daemon assigns to each KWin UUID string (`K/kwin/state.rs:153-154`, `603-611`). KDE already has a registry (uuid <-> id) behind its backend, and `KWinBackend::command` resolves every command through it (`K/kwin/mod.rs:797-806`).
5. **The macOS deadlock has more entry points than the plan lists.** The plan names `destroy_all_borders` from the event thread (`M/process_event.rs:128, 139`). A blocking main-queue dispatch under the window-manager lock also happens from the event thread at `M/process_event.rs:791` (`activate_finder`, `M/macos_api.rs:492`), and from command threads (`M/process_command.rs:294, 303, 1776, 1802, 1806`) and workspace switching (`M/window_manager.rs:1385`, `2286`). Section 3.3.
6. **Windows HWND width**: the code never narrows an HWND, so it assumes nothing about 32-bit significance (section 4). The Microsoft-documented fact that handles are 32-bit significant is not verified here.
7. **Counts** (re-measured; method in section 2.3). KDE trait: 31 (not 28, see 1). Windows `WindowsApi`: 71 distinct functions used outside `windows_api.rs` (matches), 280 call sites in `W/` plus 3 in `komorebi-bar/src/bar.rs` = 283 (earlier survey 279). The generic / Windows-only split depends entirely on the rule used; with the rule stated in 2.3 it is 41 / 30 functions and 219 / 61 sites (earlier survey 42 / 29 and 209 / 70). macOS: 14 `MacosApi` functions, 5 of 8 `CoreGraphicsApi` functions, 13 `AccessibilityApi` functions are used outside their API files; the earlier "52 raw AX sites, 33 in window.rs" does not reproduce for the total: **67** `AccessibilityApi::` sites in 12 files, 33 of them in `M/window.rs` (that part agrees).
8. **The plan's list of macOS main-thread-only work is incomplete in one respect.** The AX observer and event-tap callbacks run on main and do synchronous AX IPC to other applications there (`M/window.rs:288-350`, `M/input_event_listener.rs:96-100`): "main thread" is not just "cheap UI work".
9. **macOS has no focus-follows-mouse implementation**, only config/state fields (`grep` finds `FocusFollowsMouse` in `M/static_config.rs`, `M/state.rs`, `M/core/mod.rs` and nowhere else); KDE and Windows both have one. The plan lists focus-follows-mouse among platform subsystems; for macOS it is absent, not platform-specific.

## 2. The operation table

Conventions. "Rect" is the shared `komorebi_layouts::Rect`: `left`, `top` are the origin and **`right`, `bottom` hold the width and height**, not the far edge (`komorebi-layouts/src/rect.rs:19-28`; the conversions `From<RECT>` at `:32-41`, `From<CGRect>` at `:67-76`). "Queued" means the call returns before the platform has acted; "sync" means the calling thread waits for the platform to answer. Row numbers are for reference in later sections.

## 3. Threads, locks and who calls the platform

Common to all three trees: the window manager is `Arc<parking_lot::Mutex<WindowManager>>`; the event consumer thread takes `wm.lock()` and holds it for the whole event; command connections take it with `try_lock_for(1 s)` on UDS (`K/process_command.rs:2125`, `M/process_command.rs:1882`, `W/process_command.rs:2280`; the Windows TCP path uses a blocking `lock()`, `:2333`). The event channel producers use `try_send` on KDE and macOS (`K/window_manager_event_listener.rs:55`, `M/window_manager_event_listener.rs:54`) and a blocking `send` on Windows (`W/windows_callbacks.rs:212, 233`); see the step 5 prep entries for the channel facts, not repeated here.

Findings (KDE).

1. **Every `Backend` call from non-test code happens either at start-up/shutdown on the main thread, or from a thread that holds the WM lock.** The KWin bridge threads never call it. So a `Backend` method may block the WM lock but never the bridge.
2. **Two kinds of backend methods block their caller**, which is why finding 1 matters. `cursor_pos` blocks up to 250 ms on a reply that arrives on the bridge runtime (`K/kwin/mod.rs:841-849`). `ensure_workspaces`, `hide` when the park desktop does not exist yet, `apply_look`, `set_border_colours`, `set_focus_follows_mouse` and `shutdown` use `Handle::block_on` (`Shared::block_on` `:178-183`, uses at `:901, 931, 1007, 1027, 1097, 1114`). `block_on` from inside a tokio worker panics (tokio's documented behaviour, not re-verified here), so the code relies on no runtime thread calling `backend()`; finding 1 shows that holds today.
3. **Tests.** `with_backend` sets a **thread-local** override (`:633-635, 697-707`), so a thread spawned inside it does not see the test's fake: it falls through to `BACKEND` (unset in a test), then to a fresh permissive fake of its own in unit tests, or panics with "no backend installed" elsewhere (`:649-657`). In integration tests (`komorebi/tests/*.rs`) the library is not built with `cfg(test)`, so `test_default` returns `None` (`:670-673`) and a test must install a backend. 54 of the 60 files in `komorebi-for-kde/komorebi/tests/` mention `with_backend`, `set_backend` or `FakeBackend`; the six that do not are `power.rs`, `config_parity.rs`, `hot_reload.rs`, `no_kwin.rs`, `version.rs`, `socket.rs`. Production code that spawns a thread which calls `backend()` would work under `set_backend` but silently get a different (permissive) fake in a unit test: nothing today does (the only test-spawned thread, `K/process_command.rs:2229`, only reads a socket).
4. **`FakeBackend`** records 18 command kinds (`K/backend/fake.rs:43-81`), has a `min_sizes` table so a window can refuse a size (`:90`), and has **no failure injection**: its only error is `no such window` (`:509`). It has no frame offset (shadow) model either.

Thread-affinity findings (Windows).

1. **Documented or evident thread-affine operations are all window creation and message handling, not window manipulation.** A window must be created by a thread that pumps its messages (`W/animation/ghost.rs:10-14`); the border's Direct2D brush update must run on the window's own thread, which is why it is posted as `WM_UPDATE_BRUSHES` (`W/border_manager/border.rs:75-79, 457-459`); the `Border` is owned by the thread that created its window (`W/border_manager/mod.rs:1054-1056`); the WinEvent hook is installed on the thread that pumps (`W/winevent_listener.rs:26-53`). That `WINEVENT_OUTOFCONTEXT` callbacks are delivered on the installing thread is Microsoft's documented behaviour, not verified here.
2. **No `WindowsApi` function that acts on a managed window is documented thread-affine, and none is called from a single thread.** `position_window` alone is called from the event thread, command threads, animation threads and live-resize threads (see the list above). The code comments explain the one cross-thread cost: `SetWindowPos` waits for the target window's own thread unless `ASYNC_WINDOW_POS` is used (`W/windows_api.rs:518-520`), which is a property of the target app, not of komorebi's threads. `SetCloak` initialises COM per thread through a thread-local (`W/com/mod.rs:40-45, 68-72`), so it is callable from any thread too.
3. **Consequence for a Windows `Backend` adapter**: it can be a stateless wrapper over `WindowsApi`, callable from any thread, **except for the pieces that create windows** (borders, stackbars, ghosts, the hidden window and the WinEvent hook), which stay with their own message-loop threads and are exactly the "platform subsystems" of section 2.2.
4. **Hazard that exists today**: the hook callback blocks in `send` when the 20-slot channel is full (`W/winevent_listener.rs:59`, `W/windows_callbacks.rs:212, 233`), while the consumer needs the WM lock that a command thread may hold while itself sending into the same channel (`W/window_manager.rs:802, 809, 865`). Reading only; not reproduced (this is the plan's step 5 latent bug 2).

### 3.3 macOS: the main thread, the dispatches and the possible deadlock

**The main thread** (`M/main.rs:202-367`) is the only thread that may touch AppKit. `main` creates `NSApplication`, calls `finishLaunching` rather than `run` (`:226-230`), registers the `NSWorkspace` observer and the CoreGraphics display callback (`:232-233`), takes `CFRunLoop::current()` and installs the event tap on it (`:235-236, 322-330`), builds the window manager, starts all other threads (`:282-290`), and then **spins** in a loop: `nextEventMatchingMask(.., 0.1 s)` plus `CFRunLoop::run_in_mode(default, 0.1 s)` (`:314-349`; the comment at `:333-334` says the explicit NSApp pumping is what makes display callbacks fire on macOS Tahoe). Because of the 0.1 s bound, anything added to that run loop from another thread is noticed within 0.1 s even without a wake-up call. The main thread takes the WM lock only before the loop (`:274-280`) and after it (`:354`).

What runs on main, from callbacks: AX observer callbacks for windows (`M/window.rs:288-350`) and applications (`M/application.rs:54`), the `NSWorkspace` handler (`M/notification_center_listener.rs:183-229`, selector based, no queue argument), the CG display reconfiguration callback (`M/display_reconfiguration_listener.rs:12-30`, registered `:76`), the event tap callback (`M/input_event_listener.rs:63-100`). **None of them takes the WM lock** (no `lock()` call on `wm` in those files). They do synchronous AX IPC to other applications: the window observer reads the window id, title and, for moves, the frame (`M/window.rs:294, 330`), the tap reads the foreground window (`M/input_event_listener.rs:88-100`). The handlers hand off by `try_send` only (`M/window_manager_event_listener.rs:54`, `M/monitor_reconciliator.rs:63-67`, `M/reaper.rs`, `M/border_manager/mod.rs:168-178`). That `NSWorkspace` posts on main, and where exactly the CG callback is delivered, is Apple behaviour and not verified.

AppKit objects are created or touched on main only: `NSScreen::screens(MainThreadMarker::new().unwrap())` panics off main (`M/macos_api.rs:213`; the same in `M/splash.rs:166`); closures dispatched to main use `MainThreadMarker::new_unchecked()` (`M/border_manager/ns_window.rs:55`, `M/animation/ghost.rs:142`, `M/macos_api.rs:66`).

`exec_sync` is `dispatch_sync_f` (`dispatch2-0.3.1/src/queue.rs:118-130`): the caller blocks until the main queue has run the closure. Calling it from the main thread itself deadlocks in libdispatch (Apple documents this; not verified here). `main` reaches `destroy_all_borders` once, through `retile_all` at `M/main.rs:280`, and that is safe only because the border thread, the sole creator of borders, is started afterwards (`:282`), so `BORDER_STATE` is empty and `destroy_border` is never called. This is true by reading only.

**The possible deadlock, stated precisely (by reading, not reproduced).** Three things must coincide:

1. A thread E (the event consumer, or a command thread) holds the WM lock for the whole of a message (`M/process_event.rs:74`; `M/process_command.rs:1882`).
2. While holding it, E calls a blocking main-queue dispatch from the table above: `destroy_all_borders` (space change, `M/process_event.rs:128, 139`; `retile_all`; several commands), `hide_borders_on` (workspace switch with ghosts, `M/window_manager.rs:1385`) or `activate_finder` (`M/process_event.rs:791`).
3. The monitor reconciliator thread R has dispatched `exec_sync(closure)` for a `Resize` or `DisplayConnectionChange` (`M/monitor_reconciliator.rs:106, 383`) and the main thread has started that closure, which calls `wm.lock()` and therefore waits for E.

Then E waits for the main queue (which is inside R's closure), the main thread waits for E's lock, and neither can proceed. The existing mitigations protect only their own pair of threads: R drops the lock before its second dispatch (`:379-381`), and `apply_follows` uses `try_lock` (`M/border_manager/mod.rs:196-205`). `deadlock_detection` (`parking_lot::deadlock::check_deadlock`, `M/main.rs:151-174`) would show main blocked on a `parking_lot` mutex but cannot see that E is waiting on a dispatch semaphore, so no cycle appears in its lock graph. The exposure window is small (a display change at the instant of one of those events). The structural fix, outside this work, is that no closure run on the main thread takes the WM lock. **Relevance for the seam**: this is why consequence 4 (no `Backend` method blocks on main while the WM lock is held) is a rule the extraction must not violate; today the rule is already violated at the sites above.

**AX observers and the run loop.** `Window::observe` adds an observer source to the main run loop from whichever thread calls it: the event thread (`M/process_event.rs:614`), a command thread (`M/process_command.rs:1758`) and `main` at start-up (`M/macos_api.rs:341, 349`). Border observers are the opposite: added inside an `exec_sync` on main (`M/border_manager/border.rs:153-170`). Whether adding a source to a run loop from a thread that does not own it is safe is a CoreFoundation property that I did not verify (Apple's threading guide lists `CFRunLoopRef` as thread-safe, from memory, not checked). The code asserts it for windows and avoids it for borders.

**Thread-safety assertions in the code.** `AccessibilityUiElement` and `AccessibilityObserver` are `unsafe impl Send + Sync` (`M/lib.rs:282-284, 300-302`), `NsWindow` is `Send` (`M/border_manager/ns_window.rs:38`), `Still` (a `CGImage`) is `Send + Sync` (`M/animation/capture.rs:19-20`), and the animator clones `WindowHandle { element, app }` into lane threads (`M/animation/animator.rs:90-93`). So AX elements already travel between threads; that this is allowed by the AX API is not verified.

### 4.1 Windows: does an HWND fit in 32 bits?

The code never narrows an HWND: it is an `isize` end to end, cast to a pointer with `as_ptr!` (`W/windows_api.rs:177-181`); the socket type is `DebugWindow(isize)` (`W/core/mod.rs:273`), later `i64` by decision D15; `grep` finds no `hwnd as u32/i32/u64` except an animation delay jitter `start + Duration::from_millis(hwnd as u64)` (`W/animation/snapshot.rs:920`) that does not depend on the width. So the Windows code **assumes nothing** about 32-bit significance and does not need it. For a shared `WindowId(u64)`: a positive `isize` converts losslessly; a negative one (a sign-extended 32-bit value) would not map to a small `u64`.

Observation, not a guarantee: the Windows guest logs and state dumps from the user's earlier e2e runs (`~/e2e-w0`, read only) contain **440 distinct HWND values from 12345 to 7,804,828; none negative, none above 2^32** (`grep -rhoaE 'hwnd[\\": =]+-?[0-9]{4,}'`; 12345 looks like a test constant). Microsoft documents that handles are 32-bit significant for interoperability between 32- and 64-bit processes; I did not check that text here, so treat "HWND < 2^32" as likely but unproven (section 8).

### 4.2 macOS: acting on a window from a bare id

Today nothing on macOS acts from an id: callers hold a `Window` (cloned freely) or a bare element. `AdhocWindow` acts on an `AXUIElement` with no `Window` (`M/window.rs:1436-1530`: `minimize`, `close`, `hide`, `restore`, `raise`, used from `M/process_event.rs:594` and `M/process_command.rs:327-332`), and the animator keeps `WindowHandle { element, app }` per id (`M/animation/animator.rs:90-93`). A `Backend` that takes only a `WindowId` therefore needs a registry that owns, per id:

- the window `AXUIElement` (set frame, minimize, raise, close, alive check);
- the application `AXUIElement` and pid (focus uses the pid and the id for SkyLight, `M/window.rs:1089`, and the application's name and `main_window()` for tabbed apps, `:1105-1129`; the animator uses the app element, `M/window.rs:1065-1067`);
- the `AXObserver` (only to keep or release observation; `Window::new` creates one per window, `M/window.rs:554-570`);
- a way to learn it is dead: an AX error on any call (`M/reaper.rs:164-173`), a destroyed notification, or `Window::is_valid` (`M/window.rs:572`).

Where macOS builds the id-to-element link today: at start-up by matching the CoreGraphics list to AX windows **by title** (`M/macos_api.rs:326-349`, `M/application.rs:195-208`), and afterwards from each AX notification, where the id comes from the private `_AXUIElementGetWindow` (`M/accessibility/mod.rs:31-39`, `M/accessibility/private.rs:12-16`), which can fail (`window_id(..).ok()` at `M/window.rs:294`). The registry therefore has to be fed from both, and an id the registry has never seen is not actionable.

KDE is the precedent: its `Backend` also takes only ids and keeps an id-to-UUID table (above).

### 4.3 Where per-window platform data lives today

- **KDE**: `kwin/state.rs` `Table` (entries, `by_uuid`, `next_id`, park desktop) for backend data; `HIDDEN_WINDOWS` (`K/window_manager.rs:52, 1401`) in the core for what komorebi has hidden.
- **Windows**: nothing in `Window`; globals keyed by HWND: `HIDDEN_HWNDS` (`W/lib.rs:89`), `known_hwnds` (`W/window_manager.rs:103`), border state keyed by container id with `window_border(hwnd)` (`W/border_manager/mod.rs`), the cloak record (`W/cloaked.rs`), the live-resize and animation tables.
- **macOS**: in `Window` and `Application` themselves (element, observer, details), plus globals keyed by id: `WINDOW_RESTORE_POSITIONS` (`M/lib.rs:121`), `PARKED_WINDOWS` (`M/window.rs:121`), `ARRIVALS` (`M/arrival.rs:40-41`), the animator's `Tracks` (`M/animation/animator.rs:95-98`), the border map; and `WindowManager::applications: HashMap<i32, Application>` keyed by pid (`M/window_manager.rs:122`) and `known_window_ids` (`:146`).

### 6.1 Evidence for "a frame request returns once made; landing is observed later"

The three platforms disagree about whether a frame write has landed when the call returns, and each tree has grown a way to find out afterwards:

- **KDE**: the command is queued and goes out as the reply to a held `Poll` (`K/kwin/mod.rs:185-188, 268-300`). The trait says so: commands "return once the compositor has accepted them, not once the client has acted on them" (`K/backend/mod.rs:21-22`) and a client "may refuse the size, so the frame the window ends up with is `window_rect`, not `rect`" (`:319-320`). `window_rect` is optimistic until the `geometry` event arrives (`K/kwin/state.rs:594-600`).
- **macOS**: "An app is free to refuse a size, and many do" (`M/arrival.rs:1-12`): after a direct write the layout reads the frame back (`M/window.rs:944-972`) and, with animation on, the animator verifies each journey (`M/animation/animator.rs:6-14, 902`); both report to `arrival`, which says "Nothing in this module waits for anything or takes the lock of the window manager, so it can be called from any thread. The layout picks up what has been said the next time that it runs" (`:8-10`). `settle` does it again after a drag: "A window can be told where to go and not get there ... A quarter of a second after the drag ... the windows are looked at and any that are not where they are to be are sent there again, and looked at once more after that" (`M/settle.rs:1-9, 31`). The animator's own moves come back as AX notifications and "must not be mistaken for somebody moving a window" (`M/window.rs:300-301`).
- **Windows**: `SetWindowPos` is synchronous unless `ASYNC_WINDOW_POS` (`W/windows_api.rs:518-528`), and the same two ideas exist: `set_position` compares the frame to the layout before writing (`W/window.rs:394-396`), and after a drag the windows are looked at again after 250 ms, "a window that is busy with what an earlier move made it do is seen to be left where that put it" (`W/live_resize.rs:713-724`).

So the facts support: **a frame request may complete before, after or never at the requested size; the achieved frame is learned from events or from a separate, possibly slow, query.** They do not support "never read back": section 7, consequence 2.

## 7. Consequences for the seam

The seven consequences of plan step 7, each against the facts above. Status: CONFIRMED (the facts support it as written), CORRECTED (the plan was wrong or too strong), TARGET (not true of any current code; a rule the seam would have to make true).

**(1) The macOS backend owns an id -> {AX element, pid, observer} registry. CONFIRMED, with additions.** `Window` carries element, application and observer and is cloned into other threads (`M/window.rs:417-427`, `M/animation/animator.rs:90-93`), nothing acts from an id today (section 4.2), and KDE already has the id-to-UUID table behind its backend (`K/kwin/state.rs:153-154, 603-611`). Additions: the registry also needs the application element (focus for tabbed apps, the animator's enhanced-UI guard); the per-id bookkeeping that is global today (`WINDOW_RESTORE_POSITIONS`, `PARKED_WINDOWS`, `ARRIVALS`) belongs behind it or beside it; it has to be fed both by start-up enumeration (a title match, `M/macos_api.rs:326-349`) and by AX events (`_AXUIElementGetWindow` can fail, `M/window.rs:294`); an id it does not know must give an error, as KDE's `command` does (`K/kwin/mod.rs:797-806`). The per-window `AXObserver` can stay a platform subsystem (observation only) if the registry does not need to release it.

**(2) The contract is "`set_rect` returns once requested, never read back to confirm; landing is observed through events". CORRECTED.** Not true as stated: macOS reads back (`M/window.rs:944-972`, `M/arrival.rs`, `M/animation/animator.rs:902`), Windows compares before writing (`W/window.rs:394-396`), KDE's `window_rect` returns the request until the event replaces it (`K/kwin/state.rs:594-600`). What the facts support (section 6.1): *`set_rect` is a request. It returns when the request has been made (queued on KDE, issued on Windows and macOS), says nothing about the frame the window ends up with, and may fail only for an unknown or dead window. The achieved frame is reported by events and by `window_rect`, which a backend may serve from a cache that holds the request until an event corrects it; a backend may offer an explicit, possibly slow, read-back, which the layout calls only where it needs the truth (a refused width, the end of a drag).* The shared `FakeBackend` should be able to refuse a size (it already has `min_sizes`, `K/backend/fake.rs:90`) and to delay or drop an event, which it cannot today (no failure injection, section 3.1).

**(3) Every method is callable from any non-main thread; main-thread work hides inside the macOS implementation. CONFIRMED, qualified.** KDE: every call comes from a thread holding the WM lock or from start-up/shutdown, never from the bridge runtime, whose `block_on` would panic (section 3.1). Windows: stateless, callable from any thread; only window creation and message loops are thread-affine (section 3.2). macOS: the platform calls are already made from the event, command, reaper, settle, reconciler and animator threads (section 3.3). Qualifications: (a) "hides inside the implementation" must not mean `exec_sync`: four of the current `exec_sync` sites (`M/border_manager/mod.rs:157, 307`, `M/border_manager/border.rs:244`, `M/macos_api.rs:492`) are reached under the WM lock and are the ingredients of the possible deadlock; the hidden main-thread work should be `exec_async` with a bounded wait or data the implementation already holds (consequence 4). (b) **Five `Backend` methods exist only because KDE delegates workspaces to the compositor** (`ensure_workspaces`, `switch_workspace`, `set_window_workspace`, `window_workspace`, `current_workspaces`, `K/backend/mod.rs:408-432`; table row 18). Windows and macOS keep workspaces in the core and implement them with hide and restore (row 6). The trait cannot require them of all three: use a capability query, or split them into a sub-trait that only KDE implements and a core path for the rest. (c) `maximize` and `set_opacity` are provided no-ops today and are real on KDE and Windows only; macOS has neither (rows 16, 17), so those need the same capability treatment.

**(4) No `Backend` method blocks on the main thread; on macOS `monitors()` reads a cache refreshed by the display callback; rendering uses `exec_async`. TARGET, not current behaviour.** Current macOS: `latest_monitor_information` is a live `NSScreen` query that panics off main (`M/macos_api.rs:212-213`) and its callers run on main through `exec_sync` (`M/monitor_reconciliator.rs:106, 117, 383`). Blocking main dispatches under the WM lock exist at `M/border_manager/mod.rs:157, 307`, `M/border_manager/border.rs:153, 244`, `M/macos_api.rs:492`, plus the unbounded `rx.recv()` for border windows (`M/border_manager/ns_window.rs:135`); the bounded ones are `on_main` (`M/animation/ghost.rs:125-129`, 750 ms). The CG display callback and `NSWorkspace` handlers run on main (section 3.3), so a cache refreshed there is feasible (a `try_send` today, `M/display_reconfiguration_listener.rs:12-30`), but nothing does it yet. Corrections to the rule's wording: KDE's own contract says "Queries never block on the compositor" (`K/backend/mod.rs:179`) and is also violated, by `cursor_pos` (up to 250 ms, `K/kwin/mod.rs:846`) and by the six `block_on` methods (section 3.1); so the seam rule should be "no `Backend` method waits for the main thread of its own platform, and any method that waits for anything is listed and bounded", which Windows (`SetWindowPos` waiting for the target, unless async, `W/windows_api.rs:518-520`) and KDE also need.

**(5) Borders, stackbars, ghost/DWM, focus-follows-mouse, AX observers, the event tap, SkyLight batching and pan stay in platform crates, feeding the core through the thin event vocabulary. CONFIRMED for most; three corrections.**
- *Focus-follows-mouse* is not platform-only: KDE and Windows both implement it as a setting (`K/kwin/mod.rs:1024-1048`, `W/windows_api.rs:1224-1257`); macOS has none (correction 9). It belongs in the trait as an optional setting.
- *Borders on KDE* are drawn by the compositor and reached through `Backend::apply_look` and `set_border_colours` (`K/backend/mod.rs:473, 504`; callers `K/border_manager/mod.rs:199, 289`), so for KDE they are Backend operations, while on Windows and macOS they are the platform's own windows. The split is therefore "a look request that a backend may ignore" (KDE's `Ok(false)`) versus platform crates that draw.
- **SkyLight batching is not confined to the platform layer.** `BatchedUpdates::begin()` brackets groups of window operations from `M/monitor.rs:246, 289`, `M/window_manager.rs:1383` and `M/workspace.rs:1470-1519` (`SLSDisableUpdate` ... `SLSReenableUpdate`): "everything that changes on screen is held back until this is dropped" (`M/skylight.rs:36-45`). Any shared code that does a layout then needs a way to say "these writes appear together" (a batch or transaction scope with a default no-op). KDE already batches by construction (the `Poll` reply, `K/kwin/mod.rs:285-290`); Windows does not.

**(6) `WindowInfo` has optional metadata fields. CONFIRMED.** KDE's `WindowInfo` has `class`, `exe`, `path`, `fullscreen`, `maximized`, `normal` as plain fields (`K/backend/mod.rs:63-91`). macOS has no class, only a bundle identifier, role and subrole (`M/window.rs:842-905`), and asks the app per field over AX; Windows asks per field too (`W/windows_api.rs:866-1052`). Only `id`, `pid`, `rect` and `alive` are available everywhere cheaply; the rest should be `Option` or fetched on demand. `normal`, `fullscreen`, `maximized` have no macOS source.

**(7) macOS setup takes the main run loop from the platform's `main`. CONFIRMED.** macOS `main` owns the `NSApplication`, the run loop, the event tap and the observers and spins the loop itself (`M/main.rs:226-349`), and the shared `WindowManager` carries the run loop as a field (`WindowManager::new(&run_loop, ..)`, `StaticConfig::preload(.., &run_loop)`, `M/main.rs:260-271`). Windows and KDE `main` have no loop to run: they block on a ctrl-c channel (`W/main.rs:350-357`, `K/main.rs:372-379`). So `main` stays per platform. A shared `run` has to accept a "what to do with the calling thread" hook (park for KDE and Windows, spin the loop for macOS), and the run loop must stop being a field of the shared `WindowManager`.

**Findings the plan did not list**

- **(8) Batch/transaction scope**: see (5).
- **(9) Error types differ**: KDE `eyre::Result` (`K/backend/mod.rs:325`), Windows `eyre::Result` for some calls and `()` for `ShowWindow`-based ones (rows 5, 6, `W/windows_api.rs:668-684`), macOS `AccessibilityError` and `LibraryError` (`M/window.rs:794-915, 1084`). A shared error type must carry "the window is gone", because macOS uses a failed write as its signal for that (`M/reaper.rs:164-173`).
- **(10) `center_cursor_in(&Rect)` is only honest on Windows and macOS**; KDE ignores the rect (row 14). Either the method becomes "centre on this window" or KDE's contract gets a caveat.
- **(11) Hide is observable on macOS and Windows-`Hide`/`Minimize`**, because it changes ordinary window state (a corner position, `SW_HIDE`, minimized), whereas KDE's park desktop and Windows' `Cloak` do not. The core's habit of keeping its own table of what it hid (`HIDDEN_WINDOWS`, `HIDDEN_HWNDS`, `PARKED_WINDOWS`) exists for that reason and the seam must keep the distinction ("hidden by komorebi" versus "minimized by the user") visible to the core.

## 9. Findings from the 7c adapters

Step 7c wrote `WindowsBackend` (`komorebi/src/windows_backend.rs`) and `MacosBackend` (`komorebi-for-mac/komorebi/src/macos_backend.rs`) over the existing static functions, to learn which methods of the shared trait (`crates/komorebi-backend`) cannot be implemented without changing what the daemon does. Both compile (Windows: clippy `-D warnings` clean; macOS: fake-CC `cargo check` 0 errors) and neither is used by its daemon. They have never run: everything below comes from reading the code while writing the adapter, and "not verified" means exactly that. `K/` is `komorebi-for-kde/komorebi/src/`; `W/` and `M/` as in section 1.

**Verdict.** All 14 required methods and the 4 capabilities could be written on both platforms, so the trait did not have to change. Eleven of them carry a semantic difference that the doc comments of the trait already allow (a request, a platform-defined read) or that the adapter had to choose; those are listed here so steps 8 and 11 decide them knowingly. Nothing in this section is a reason to change the trait yet; the three candidates are marked PROPOSAL.

### 9.1 Windows (`WindowsBackend`)

| Method | What the adapter does | What differs from the daemon's own call |
|---|---|---|
| `windows()` | `WindowsApi::alt_tab_windows()` (`W/windows_api.rs:763`), each one read with `info` | **Cannot be written faithfully.** The candidate list the daemon uses is `load_workspace_information` (`:437`), which filters inside the `enum_window` callback while filling the containers of a `WindowManager`. The adapter has no manager, so it lists alt-tab windows, a superset (no `should_manage`, no ignore or float rules). |
| `window(id)` | `IsWindow`, then one call per field (`process_id`, `title`, `class`, `exe`, `path`, `is_iconic`, `is_zoomed`) | `fullscreen` and `normal` are `None`: komorebi decides both in the core, there is no OS query. An error reading the frame leaves `rect` at the default, indistinguishable from a window at the origin (PROPOSAL: `rect: Option<Rect>` or an error). Five or six kernel calls per call, where KDE answers from a table: do not call it per frame. |
| `monitors()` | `valid_hmonitors()` then `WindowsApi::monitor(hmonitor)` for each | `monitor` re-enumerates every display for each handle (quadratic) and reads the global `DUPLICATE_MONITOR_SERIAL_IDS` (a duplicated serial becomes `None`). Physical pixels, the `Monitor.id` is an `isize` carried bit for bit through `MonitorId::from_hmonitor`. |
| `cursor_pos()` | `GetCursorPos`, an error is `None` | The error is dropped. |
| `set_rect` | `Window::set_position(rect, false)` | `top` (raise to the front in the same `SetWindowPos`) has no place in the trait: it is `false`, a caller raises separately, so one `SetWindowPos` becomes two. `Window::set_position` also keeps its slide-in animation, the live-resize guard (returns `Ok` while the user holds the window) and the early return when the frame is already right (`W/window.rs:329-370`): the call can return `Ok` without writing, which fits "a request" but not "the window will be there". Synchronous by default (waits for the target's thread; see unverified 7). |
| `focus` | `Window::focus(mouse_follows_focus)` | Matches the trait, including the cursor centring. When the window is still sliding in (`transition::is_entering`) the focus is **deferred** and `Ok` is returned. |
| `raise` | `Window::raise` (raises without activating, and the border) | Matches. |
| `hide`, `restore` | `Window::hide`, `Window::restore` | They return `()`: `ShowWindow` and the cloak result are ignored, so `WindowGone` is told only by an `IsWindow` check before the call (a race). They also hide or show the window's border and write `HIDDEN_HWNDS`, and are skipped while a workspace slide owns the window (`is_exiting`, `is_entering`). The default hiding behaviour `Cloak` is not observable by the user; `Hide` and `Minimize` are (finding 11). |
| `minimize` | `Window::minimize` | Silently does nothing for an exe that contains `komorebi-bar`, and returns `Ok`. No error is possible (`()`). |
| `unminimize` | `WindowsApi::restore_window` (`SW_SHOWNOACTIVATE`) | Windows has no unminimize: this is the restore the hiding behaviours use, **without** the `HIDDEN_HWNDS` and border bookkeeping of `Window::restore`. It does not activate. |
| `close` | `Window::close` (`PostMessage WM_CLOSE`) | Matches; the only call with a real error (a failed post), turned into `WindowGone` when the window is gone. |
| `center_cursor_in` | `WindowsApi::center_cursor_in_rect` | Matches (and the one place the rect is honoured, finding 10). |
| `monitor_from_point` | `WindowsApi::monitor_from_point` | **Overrides the trait default** because Windows uses `MONITOR_DEFAULTTONEAREST`: never `None`. The trait documents this; shared code must not use `None` to detect "off screen". |
| `maximize` | `Window::maximize` / `unmaximize` | `()`-returning; removes the window from `HIDDEN_HWNDS` as the daemon does. |
| `set_opacity` | LAYERED extended style, then `WindowsApi::set_transparent(hwnd, alpha)` | **Not what the daemon calls.** `Window::transparent`/`opaque` take the alpha from `transparency_manager::TRANSPARENCY_ALPHA` (a global, not an argument) and may animate (`TransparencyRenderDispatcher`). The adapter writes the plain value both end in, with no animation and no manager bookkeeping. |
| `set_focus_follows_mouse` | `enable_`/`disable_focus_follows_mouse` (the system setting) | The komorebi-implemented focus follows mouse (`W/process_movement.rs`) is a different mechanism with its own thread and is not started or stopped by this; the daemon today picks one by configuration. Both are "focus follows mouse"; the trait method means the OS setting. |
| Workspaces (5) | `Unsupported` | By design: komorebi's own workspaces. |
| Batch | default no-op | Windows does not batch. |
| Thread | any thread | The calls are stateless except for the statics named above (`HIDDEN_HWNDS`, `DUPLICATE_MONITOR_SERIAL_IDS`, the transition and live-resize tables), which are behind locks. `set_rect` and `raise` wait for the target window's thread unless `WINDOW_HANDLING_BEHAVIOUR` is `Async`: the bounded-wait rule of section 7(4) is not met by Windows today. |

### 9.2 macOS (`MacosBackend`)

| Method | What the adapter does | What differs from the daemon's own call |
|---|---|---|
| (registry) | `Mutex<HashMap<u32, Window>>` with `register(Window)` and `forget(id)`; every method clones the `Window` out | **The trait needs a feeder the trait does not have.** The daemon must call `register` wherever it creates a `Window` (start-up enumeration by title, AX events) and `forget` on destroy. `Window` carries the element, application and observer, and the adapter keeps the whole clone, so the registry holds the observer too (consequence 1 said the observer could stay outside: it cannot while `Window` is the unit). An id not in the registry is `WindowGone`, which is also what a window the daemon never registered looks like. |
| `windows()` | the registry's windows that are still valid | **Cannot be written faithfully.** The CoreGraphics list joined by title with the AX elements (`M/macos_api.rs:312-374`) lives in `load_workspace_information`, which fills a `WindowManager`. The list is only as complete as the registry. |
| `window(id)` | AX round trips: `is_valid` (attribute names), frame (two reads), title, exe, path, `AXMinimized` | There is no existing "is minimized" query, so the adapter reads `AXMinimized` itself. A dead window gives `None`, so "never known" and "dead" cannot be told apart (the trait allows both). `class`, `fullscreen`, `maximized`, `normal` are `None`. A frame read error leaves `rect` at the default (same PROPOSAL as Windows). Four or more IPC calls to the app per call: slow and blocking on a hung app. |
| `monitors()` | a cache; `refresh_monitors(MainThreadMarker)` fills it from `latest_monitor_information` | **A change in how the daemon works, not just an adapter.** Today every caller runs on main (`exec_sync`). The cache has to be refreshed by the display callback on main (a `try_send` today, `M/display_reconfiguration_listener.rs:12-30`); before the first refresh `monitors()` is an `Err`. The `MainThreadMarker` argument makes a call from another thread a compile error. This is the TARGET rule of consequence 4 made real. |
| `foreground_window` | `MacosApi::foreground_window_id` | Matches (`None` when any AX step fails). |
| `cursor_pos` | `MacosApi::cursor_pos` | Matches, always `Some`; floats are truncated to `i32`. |
| `set_rect` | `Window::set_position` | May write directly or hand the move to the animator, and honours the drag `Snap` state (`M/window.rs:915-940`): a request, as the contract says. A failed write asks `is_valid` to decide between `WindowGone` and a platform error (the reaper's trick, a second round trip inside the error path). |
| `focus` | `Window::focus` | Matches (SkyLight `set_front_process`, then `AXMain`; tabbed apps use `main_window`). Error is `LibraryError`. |
| `raise` | `Window::raise` | **Also focuses**: macOS has no raise without focus (`AXMain` and `AXFocused`). |
| `hide` | `Window::hide(hiding_position)` | **The trait has no place for two inputs `hide` needs.** The corner (`WindowHidingPosition`) is configuration of the monitor; `MacosBackend::new` takes one for all windows. And `hide_on(position, screen)` wants the display the window's monitor owns, "since a window that hangs over the edge is not always on the display the lookup by position finds" (`M/window.rs:610-615`); the adapter passes none and takes the lookup. PROPOSAL (step 11, not now): hide stays as it is and `MacosBackend` learns each window's monitor at `register`. |

| `minimize`, `unminimize` | `Window::minimize`/`unminimize` (`AXMinimized`) | Match (both need `&mut self`; the adapter clones). |
| `close` | `AdhocWindow::close(element)` (presses the close button) | The daemon calls it on the foreground element; here by id. `Ok` when the window has no close button. |
| `center_cursor_in` | `MacosApi::center_cursor_in_rect` | Matches. |
| `monitor_from_point` | `MacosApi::monitor_from_point` (CoreGraphics) | Matches: `None` outside every display. |
| Capabilities | none | By design (rows 16 to 19). |
| Batch | a stack of SkyLight `BatchedUpdates` guards | Matches the daemon's own brackets. Not verified: that nested `SLSDisableUpdate` calls count (the daemon nests none today). The guard holds the main connection id, so it is `Send`; `SLSReenableUpdate` from another thread than the one that disabled is not verified. |
| Thread | any thread except main for everything but `refresh_monitors` | Not verified: whether `hide_on(.., None)`'s lookup by position (`M/window.rs:616-676`) reaches an `NSScreen` and so needs main; if it does, `hide` breaks the rule until the screen is passed (see `hide`). |

### 9.3 What this means for the trait

1. **No change was needed to write both adapters.** The capability query, the batch scope, `WindowGone` and the optional fields were all used, and each was necessary: macOS answers `Unsupported` for all four capabilities, Windows for one; `WindowGone` is built from a pre-check on Windows (results ignored) and from a re-check on macOS and KDE; `None` fields are used on both.
2. **PROPOSAL A: `WindowInfo::rect` can fail** on both platforms (a frame read is an API call). If the core must tell "at the origin" from "unknown", the field becomes `Option<Rect>`. Decided not to change it now: KDE cannot fail, and the shared core has no consumer yet.
3. **PROPOSAL B: `hide` has hidden inputs on macOS** (corner, monitor). Left to step 11, where the registry learns the monitor at registration.
4. **PROPOSAL C: `windows()` is a start-up operation on Windows and macOS** (the filtered list needs the core's rules), and the trait documents it as slow. If the core wants one candidate list, the filter has to move into shared code with the window rules as an argument.
5. **The adapters add non-trait API that the daemons must call** (`MacosBackend::register`, `forget`, `refresh_monitors`; `MacosBackend::new(hiding_position)`). That is the cost of keeping `Window` as it is until step 11(ii).
