# komorebi for KDE Plasma compared with komorebi for Windows and for macOS

> **STALE (snapshot of 2026-10-27, kfw 173aa802, kfm 125a9a5):** this comparison predates the consolidation. The three programs now share `crates/` (protocol, config, collections, transport, backend, core, settings, komorebic-core) and one `komorebi`, `komorebic`, `komorebi-client` and `komorebi-bar` package, so counts of duplicated commands, messages and keys below are out of date, and `scripts/compare-gen.py` no longer runs against the current tree (it fails with `cannot find '^enum SubCommand'`, because the command definitions moved to `crates/komorebic-core`). For what is shared and what differs on purpose now, read the repository-level [docs/dev/ARCHITECTURE-UNIFIED.md](../../../docs/dev/ARCHITECTURE-UNIFIED.md) and [docs/dev/core-model.md](../../../docs/dev/core-model.md). The platform-difference tables (KWin versus Win32 versus AppKit mechanisms) remain a fair description of the platform layers.

This document compares komorebi for KDE Plasma on KWin and Wayland (kfde) with komorebi for
Windows (kfw), the original, and komorebi for macOS (kfm). It is written for a reader who knows
komorebi on one of those two systems and wants to know what is the same on KDE, what is different,
what KDE does by itself that komorebi does on the other systems, and what is not supported.

It states facts that can be checked against the code, and does not assign value judgments. "kfw
draws the borders itself and kfde asks the compositor to" is a fact. "The compositor's borders are
better" is not, and is not said here. The reasons behind kfde's choices are in
[DESIGN.md](DESIGN.md), where they are opinions and say so.

It is written for kfde, so it leans toward kfde, and it was written from the sources of the three
programs, not from running them side by side. Where something could not be verified, it says so.
A correction is welcome.

## How to read this document

Every table in a marked block is generated by `scripts/compare-gen.py` from the source trees
of the three programs, so a count or a name in it is what the code had when the block was last
generated. The text around the tables is written by hand and states what the tables say.

```sh
python3 -I scripts/compare-gen.py --update docs/dev/COMPARE.md   # rewrite the blocks
python3 -I scripts/compare-gen.py --check docs/dev/COMPARE.md    # exit 1 when one is stale
```

The script reads this checkout and checkouts of [kfw](https://github.com/LGUG2Z/komorebi) and
[kfm](https://github.com/LGUG2Z/komorebi-for-mac) (`~/komorebi` and `~/komorebi-for-mac` by
default; `--kfw` and `--kfm` name others). Continuous integration has neither checkout, so it
does not run the script: a change to a command, a message, a key of `komorebi.json`, an event or
a method of `Backend` is followed by `--check` on a machine that has them, and by `--update` and
a read of the text around the block when it reports a stale one. The script also checks the
hand-written notes it holds (why a Windows command has no counterpart, which KWin call stands in
for a Win32 one) against the sources, and the sentences of this document that depend on a
generated fact, and stops on a note or a sentence that is no longer true. The revisions it read
are:

Terms used below:

- **KWin's script** (the bridge) is a small JavaScript program that komorebi loads into KWin. It is
  the only code of kfde that runs inside the compositor, and it contains no window manager logic.
- **A workspace** is komorebi's name for one of the desktops of a monitor, in all three programs.
- **A parking desktop** is a KWin virtual desktop that nobody looks at, which kfde moves windows to
  in order to hide them.
- **The strip** is the scrolling layout of kfm, in the crate `komorebi-scrolling`. Since upstream's
  `next` branch it is also what the `Scrolling` layout of `komorebi-layouts` is laid out with, in
  kfde too ([scrolling-next.md](scrolling-next.md)).

## What is the same

### One tiling model, and the same layouts

The model is the same in all three programs: a list of monitors, each with workspaces, each with
containers, each with windows. kfde adds no layer to it. The layouts come from the crate
`komorebi-layouts`, which kfw owns and kfm and kfde use as a git dependency:

<!-- gen:layouts -->
| `DefaultLayout` | kfw | kfm | kfde |
|---|---|---|---|
| `BSP` | yes | yes | yes |
| `Columns` | yes | yes | yes |
| `Rows` | yes | yes | yes |
| `VerticalStack` | yes | yes | yes |
| `HorizontalStack` | yes | yes | yes |
| `UltrawideVerticalStack` | yes | yes | yes |
| `Grid` | yes | yes | yes |
| `RightMainVerticalStack` | yes | yes | yes |
| `Scrolling` | yes | yes | yes |

The crate each tree builds: kfw: `komorebi-layouts` in the tree; kfm: `komorebi-layouts` at git rev `f08aa55`; kfde: `komorebi-layouts` at git rev `f08aa55`.

Compared file by file with the crate of kfw, kfm: 0 of 13 source files differ from the ones of kfw; kfde: 0 of 13 source files differ from the ones of kfw.
<!-- /gen:layouts -->

The layouts of `komorebi-layouts` are calculated by the same code in the three programs, so the same
windows in the same order get the same rectangles, apart from what the window manager takes off for
the work area, the padding and the borders. The exception is the `Scrolling` layout, which is laid
out with the strip of `komorebi-scrolling` in kfm and in kfde, and not in kfw before its `next`
branch (see the section on configuration). What differs between the programs is
what the system does with the rectangles: the next sections.

### One configuration file, largely portable

A `komorebi.json` written for kfw or kfm loads in kfde. The keys that kfde does not read are
accepted and ignored, not rejected. The tables of the sections on configuration say which keys
those are, and why.

### No key of komorebi.json is read only on KDE

<!-- gen:keys-kde-only -->
none

That is by decision: a file should load on every platform that has the feature
([why](DESIGN.md#why-does-one-komorebijson-work-on-every-platform)). The keys that mean something
else on KDE, or do less, are these:

<!-- gen:keys-differ -->
| Key | Level | What is different on KDE |
|---|---|---|
| `border_width` | top level | At most 20 px: the effect draws the ring in the window's shadow, and a window without a shadow has none. While borders are drawn, the layout leaves `border_width` plus `border_offset` on each side of a window, also past 20. |
| `border_colours` | top level | Six colors, one for each kind of window, when komorebi's build of the border effect is installed. With the stock effect only `single` and `unfocused` take effect, and komorebi says so once in its log. |
| `animation` | top level | `style` is the Qt easing curve of that name (`EaseInOutSine` is `InOutSine`) and a custom cubic Bezier curve is an ease out, when komorebi's build of the Geometry Change effect is installed; the stock effect always eases out exponentially. `fps` is read and ignored: the compositor animates at the refresh rate of the screen. |

### Workspaces are KWin's virtual desktops

kfw and kfm have a workspace layer of their own: komorebi keeps a list of workspaces for each
monitor, and when one is left it hides the windows of that workspace, because Windows and macOS
have no virtual desktop API to ask. On KDE, KWin 6.8 can give each output its own current desktop,
so komorebi's workspace `i` is KWin's desktop `i` on every monitor, and each monitor shows one at a
time. A switch is one request per monitor, and KWin shows, hides and focuses. komorebi
follows a switch made by something else (the pager, a shortcut, an application raising a window)
and answers it with no command. [Why](DESIGN.md#why-are-komorebis-workspaces-kwins-virtual-desktops)
is in DESIGN.md.

This has consequences that are measured, or read from KWin's sources:

- A switch made by an application raising a window produces one focus event and one switch
  (spike 10, 2026-10-27). Answering a switch with commands makes KWin and komorebi fight: a design
  in which komorebi did the hiding flipped between two workspaces about 280 times a second, because
  KWin delivered focus events it had generated before it applied the commands, and komorebi read
  them as new intent. komorebi therefore issues no commands in reply to a switch.
- The workspaces are visible in the pager and in the overview: they are the user's desktops, and a
  stop leaves them in place (it removes the parking desktop).
- Desktops are global: every monitor has as many as the largest workspace count, and the name of a
  desktop is shared by the monitors (the first monitor's, where they differ).
- A window that komorebi does not manage (a dialog, an ignored application) belongs to the desktop it
  opened on, and goes out of view with it. kfw and kfm hide what a workspace holds (its containers,
  its floating windows and its monocle) when they leave it, so a window they do not manage stays
  visible across workspaces.
- The floor is KWin 6.8, because per-output desktops arrived there. Older KWin versions were not
  tested. At time of writing (2026-10-28) the versions run are 6.8.1 (the spikes) and 6.8.2 (the VM
  suites), in Plasma 6.8.1 and 6.8.2.
- komorebi turns `PerOutputVirtualDesktops` on in `kwinrc` when it starts and puts it back when it
  exits. It edits the file itself: `kwriteconfig6` was not on the path of the user service in the
  first live run.

### Hiding windows: cloaking, a corner, or a parking desktop

komorebi hides windows for a stack (the other windows of a container) and for a monocle (the other
containers). kfw offers three ways, chosen with `window_hiding_behaviour`: cloak (an undocumented
Win32 call), minimize, and the end-of-life `SW_HIDE`. kfm moves the window to a bottom corner of
its display, which `window_hiding_position` of a monitor chooses. kfde moves the window to a
parking desktop and moves it back, and there is nothing to choose. The scrolling layout needs none
of this: KWin keeps a window at a position outside the screen when it is moved there.

Three ways were measured on six tiled windows (spike 3, 2026-10-26, KWin 6.8.1):

| Way | Spurious focus events | Geometry restored |
|---|---|---|
| minimize | 2 (KWin picks a new active window as each window minimizes) | 6 of 6 |
| parking desktop | 0 | 6 of 6 |
| a position outside the screen | 0, but the windows stay mapped on the current desktop (task switcher, overview) | 6 of 6 |

KWin saves a virtual desktop in `kwinrc` the moment it is made, so a run that dies leaves the
parking desktop for the next session. komorebi removes it on exit, and the next start finds a stale
one, sends its windows home and removes it. A parked window still appears in the task manager unless
that is set to show the current desktop only (by construction, not measured).
[Why a parking desktop](DESIGN.md#why-are-the-windows-behind-the-front-one-of-a-stack-moved-to-a-parking-desktop)
is in DESIGN.md.

### Borders: komorebi draws them, or the compositor does

kfw draws a topmost tool window for each border, with Direct2D, and kfm an `NSWindow` for each. kfde draws nothing: the
KDE Rounded Corners effect draws the outer outline of every window, and komorebi writes its settings
to `kwinrc` and tells it to read them again. KWin keeps the copy of `kwinrc` it read at start, so
komorebi asks for a reconfiguration every time, also straight after it loads the effect.

The limits, as of 2026-10-27:

- The ring is drawn in the window's shadow, so a window without a shadow has none, and its thickness
  is at most 20 px. That is why kfde has no counterpart of `remove_titlebar_applications`: removing
  the title bar removes the shadow.
- The stock effect has a color for the active window and one for the others. komorebi's build of it
  takes a color for each window over D-Bus (`org.komorebi.BorderColours1`), which gives the six kinds
  of kfw's rules: `single`, `stack`, `monocle`, `floating`, `unfocused` and `unfocused_locked`.
  Without that build, every kind falls back to `single` and `unfocused`, and komorebi says so once in
  its log.
- KDE Rounded Corners 0.10.0 draws the ring about 24 px too low on KWin 6.8 (measured on screenshots
  of KWin 6.8.1). kfde builds 0.11.0, which nixpkgs has too at time of writing (2026-10-28).
- KWin finds effects when it starts, so an effect installed later is not loaded until the next
  login.

[Why the compositor draws the borders](DESIGN.md#why-does-the-compositor-draw-the-borders-and-not-komorebi),
[why the effects are patched](DESIGN.md#why-are-the-effects-patched) and
[why the border is the outer outline](DESIGN.md#why-is-the-border-the-outer-outline-of-the-effect)
are in DESIGN.md.

### Animation: komorebi moves the window step by step, or the compositor animates

kfw and kfm animate by moving the window a little at a time, at `animation.fps`. kfde sends the final
rectangle and the Geometry Change effect animates the move, so `fps` has nothing to map to: the
compositor animates at the refresh rate of the screen. The styles are Qt's easing curves of the same
name, which komorebi's build of the effect reads from a `Curve` setting. The stock effect eases out
exponentially, whatever the style says. Cross-fading is off.

KWin refuses effects that animate under software rendering, which includes every virtual machine the
tests run in, unless `KWIN_EFFECTS_FORCE_ANIMATIONS=1` is in KWin's environment. A screenshot cannot
show a short animation, because `spectacle` takes seconds and the curve is front-loaded: the look test
uses a 30 s animation to see the effect at work.

### Transparency, themes and wallpapers

Transparency is KWin's window opacity, set from the same rules as kfw. A window drawn through the
border effect comes from a texture with its opacity in it, which the effect redrew only when the
contents changed. komorebi's build redraws it when the opacity changes.

A wallpaper is set through the Plasma shell, over D-Bus (`org.kde.PlasmaShell`), for one screen. The
shell keeps one wallpaper for each screen, not for each virtual desktop, so komorebi sets it when a
workspace comes into view, as kfw and kfm do. If the shell is not running, komorebi tries again for
about half a minute and then says once that it leaves wallpapers alone. A palette made from a
wallpaper is cached in `$XDG_CACHE_HOME/komorebi`, by the name of the picture and a hash of its
path, size and time of change; a large picture takes seconds (not measured further).

### Focus follows mouse

kfw has two implementations to choose from, `Windows` and `Komorebi`, and calls the first legacy. kfm
has none. kfde asks KWin to use its focus policy, "focus follows mouse", with the same result for
both names, and puts the user's policy back when the setting is turned off or komorebi exits. KWin
waits for the pointer to settle before it moves the focus: `DelayFocusInterval`, 300 ms by default
in KWin 6.8.1. kfde sets it to 0 while the setting is on, and puts the user's value back with the
policy; why 0 is not recorded
([DESIGN.md](DESIGN.md#why-is-focus-follows-mouse-kwins-own-focus-policy)).

### Maximize and fullscreen

`toggle-maximize` is kfw's command, and does KWin's maximize on KDE: the window leaves the layout
and goes back to its tile when toggled again, and the panel is respected. A window that the user
maximizes (the title bar, a double click, a shortcut) is the same from then on: the commands that act
on the layout do nothing until it is restored. [Why](DESIGN.md#why-does-a-maximized-window-leave-the-layout-instead-of-being-given-the-work-area)
is in DESIGN.md. A fullscreen window covers its monitor, komorebi never moves it, and it is put back
in its tile when it leaves fullscreen. kfw has no code for fullscreen, and kfm has one
mention of it in its reaper.

## Dragging

All three programs let the user move a tile by dragging it and resize it by dragging an edge. KWin
reports where the pointer has the edge at every step of a resize
(`interactiveMoveResizeStepped`), so in kfde the neighbors follow the edge while it is dragged, and
not only when it is let go. The way a drag is measured, from the frame the window had when the drag
began, and granted as far as the layout can take it, is written down in
[drag-resize.md](../drag-resize.md), for the three programs. The frame KWin reports at the end of a
resize lags the pointer by a moment ([PLATFORM.md](PLATFORM.md#how-clients-answer-a-frame)). kfm
reads the frame of a window with an accessibility call when it needs it (`MacosApi::window_rect`);
whether that frame lags was not measured.

## Key bindings

kfw and kfm leave the keys to a separate program: kfw uses whkd, or AutoHotkey, kfm uses skhd, and
the program runs `komorebic`. On Plasma under Wayland no program sees the keys of another, so kfde
cannot do that: the keys are KDE's global shortcuts, in one of two ways, and komorebi reads the same
three formats a hotkey daemon would (`skhdrc`, `whkdrc`, `sxhkdrc`).

| | kfw | kfm | kfde |
|---|---|---|---|
| Who sees the keys | whkd, or AutoHotkey | skhd | KWin, through KDE's global shortcuts |
| The file the user writes | `whkdrc` | `skhdrc` | `skhdrc`, `whkdrc` or `sxhkdrc`, each read by a parser written for komorebi |

The measurements that decide when each is used, at time of writing (2026-10-27), on aarch64 under HVF
with four cores, KWin 6.8.1:

| What | Result |
|---|---|
| A static shortcut, key to the start of its `Exec` | 165 to 436 ms, median 233 ms, 8 runs of 8 |
| The daemon, key to the signal it gets | median 2.5 ms (min 2.2, max 3.9), 20 of 20 delivered |
| 60 calls to `setInactive` and `setShortcutKeys`, pipelined | answered in 2.4 ms in total |
| A native multi-key shortcut (`Meta+A, B`) | did not fire: the second key reached the focused client |
| A client killed after registering a key | the grab stays, and the key is swallowed, until `unRegister` |

The last two are why the daemon emulates chord chains, and why the module's unit releases the keys
when the daemon stops. A static shortcut works with the daemon stopped and shows in System Settings,
but costs about 0.2 seconds on each press; the daemon's keys are only as reliable as the daemon. The
default mode is the daemon for every binding (`keybindings.mode = "engine"`), which these
measurements favor ([why](DESIGN.md#why-does-the-engine-handle-every-binding-by-default), which
also says that the default is still open for a decision), and `auto` and `static` use shortcut
files for the bindings that can be one.

What is not emulated, and approximated, is listed in
[the user guide](../usage/keybindings.md#what-is-realized-and-what-is-not): side-specific modifiers,
mouse buttons, skhd's `fn`, and the sxhkd chain that a wrong key does not end. The reasons are in
DESIGN.md: [why some bindings are shortcut files](DESIGN.md#why-are-some-bindings-shortcut-files-and-the-others-the-engines)
and [why the engine grabs keys instead of using KDE's key sequences](DESIGN.md#why-does-the-engine-grab-and-give-back-keys-instead-of-using-kdes-own-key-sequences).

Keystrokes over RDP: KDE's shortcuts sit inside KWin's input pipeline and see them, and `swhkd`
reads the kernel's input devices and would not (read from the sources of KRDP and swhkd, not run).
Keys sent over RDP to a session were not verified end to end: the scripted client fails NTLM
against KRDP, and a real client was not tried.

## Multiple monitors, sleep and lock

All three programs have a monitor reconciliator: a thread that takes notifications one at a time to
move the windows of a monitor that went away and to bring them back. In kfw a hidden window
(`WM_DISPLAYCHANGE`) feeds it, and in kfm a display reconfiguration callback. In kfde the script feeds
it, with the whole list of outputs whenever KWin's changes, and so does the code that hears of a wake
or an unlock. The daemon takes the windows of an unplugged monitor over (each container, a stack whole, to the workspace of the same number), keeps what is left
of the monitor for when it comes back, and follows a window that something else moved to another
output. A moment after each notification (1.5 s) it looks at every window again, because KWin has
moved some. A monitor that changes size or scale is tiled again: every coordinate komorebi uses is
KWin's logical one. [Why](DESIGN.md#why-does-komorebi-take-the-windows-of-an-unplugged-monitor-over-itself)
is in DESIGN.md.

For the screen lock, kfm has `ScreenLock` and `ScreenUnlock` events, and kfw registers for power and
session notifications. kfde listens on D-Bus: logind's `PrepareForSleep` for a wake, and KDE's screen
saver `ActiveChanged` for a lock. With the screen off or locked KWin sends clients no frame callbacks,
so what komorebi asked for in that time is not done: komorebi waits 600 ms after an unlock and 2.5 s
after a wake and looks at every window again. The lock screen is a window of KWin's that is in no
task list and on every desktop; komorebi does not manage it.

At time of writing (2026-10-27) a real suspend and resume was not tested: the QEMU guests have no
way to wake from one. The signals are tested on private buses, and the lock screen against a real
KWin in a Plasma session. [PLATFORM.md](PLATFORM.md#sleep-and-lock) says so too.

## Checking the configuration

kfw and kfde have `komorebic check`, and kfm has none. kfw's reads the files in the configuration
home (`komorebi.json`, `komorebi.ahk` and `whkdrc` among them) and shows what is wrong with them.
kfde's reads `komorebi.json` the way the daemon will, tells a key of another platform from a typo
(with the nearest key that is a setting), looks at the key binding file and at whether it has been
made into KDE shortcuts, and then looks at the desktop: a Plasma session on Wayland, KWin 6 on the session bus, komorebi's
script in KWin, which build of each effect is installed, the Plasma shell when there are wallpapers,
and what starts komorebi at login. It exits with status 1 when something stops komorebi from working
(a file that is not JSON, no KWin), and 0 with warnings when it only will not do what was meant.
`--komorebi-config FILE` checks another file and `--configuration-only` leaves the desktop out; the
first flag is kfw's too.

kfw's `check` also asks GitHub for the latest release. kfde's does not look for a newer release, and
it does not know the AutoHotkey and PowerShell files of Windows.

## What kfw and kfm have that kfde does not

From the tables above, and from what has no row in them:

- The bar. `komorebi-bar` is not ported: the Plasma panel is used, and the work area accounts for it
  (a panel moved is a change of the work area, and the tiles are made again).
- The stackbar and its settings. A stack is cycled with `cycle-stack` and `focus-stack-window`.
- Custom layouts, which kfw has and kfm does not. Not supported yet.
- The Win32 workarounds of the "Win32 quirks" group, the AutoHotkey and PowerShell configurations,
  the named-pipe subscribers, and whkd as a separate program.
- The license check and the splash screen of the macOS and Windows builds.
- The tab and title bar commands (`remove-title-bar`, `toggle-title-bars`).

## What kfde has that kfw and kfm do not

- Native workspaces: they show in KWin's pager and overview, and KWin focuses the window of the
  desktop it switches to.
- Borders, animation, transparency and focus follows mouse as a compositor does them, and `check`
  for a desktop.
- Key bindings that work from a physical keyboard, the QEMU console and RDP, with modes, chords and
  scopes realized by the daemon, and the `skhdrc`, `whkdrc` and `sxhkdrc` formats.
- A NixOS module (`services.komorebi`) with a user unit, the effects, and the key bindings as options,
  and a version check of KWin. kfm has a module for nix-darwin, in its own form.
- A test suite that runs the window manager against a real KWin in virtual machines, and a `Backend`
  that tests replace with a desktop in memory. [vm-tests.md](vm-tests.md) describes it.
